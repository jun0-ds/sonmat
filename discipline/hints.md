# 도메인 힌트 (Domain Hints)

판단이 필요한 실패를 행동하는 순간에 떠올리게 하려고 둔다. 교과서 지식이 아니라, Claude가 따로 신경 쓰지 않으면 틀리거나 건너뛰는 것들이다.
모든 worker에게 core.md와 함께 넣어 준다. worker는 지금 작업에 맞는 항목만 적용한다.

힌트는 가장 약한 집행 수단이다. 특정 명령·파일·이벤트에서 기계적으로 가려낼 수 있는 실패는 훅·가드·도구로 막고, 여기에는 판단이 필요하고 포착 신호가 구체적인 것만 둔다. 이 파일은 8,000자를 넘기지 않는다. 특정 작업에서만 필요한 규율은 별도 파일(`spec.md`, `codex-full-access.md`)에 두고 필요할 때 읽는다. 힌트마다 근거가 된 함정 목록은 메모리 쪽 `hint-evidence.md`에 있다.

## 증거와 출처 (모든 도메인)

- **증거보다 넓게 주장하지 않는다.** passed / fixed / done / works / not present라고 쓰기 전에, 그 주장이 포괄하는 모집단(계정 등급, 클라이언트, 설치 대상, URL, 환경, 서비스 경로)과 실제로 본 표본을 밝힌다. 대표 하나는 표본일 뿐 통과가 아니다. 배포 성공, HTTP 200, 종료 코드 0, "parsed / listed / installed", 커밋 조상 관계는 자신이 관찰한 단계만 입증할 뿐 사용자가 보는 결과를 입증하지 않는다. 검증 명령은 assertion이 실제로 실행됐다는 것도 보여야 한다(예상한 성공 표지나 assertion 개수). 요청자가 결과를 말했으면 그 문장을 검사 목록으로 삼아 각 절을 증거나 "unverified"와 짝짓는다. 검증할 수단이 없으면 보고 첫 줄에서 밝히고, 가까운 대리 지표로 그 자리를 메우지 않는다. 예: 2026-09-29에 최상위 계정 하나로 한 운영 QA가 통과로 보고됐지만, 하위 등급·신규 가입·프로필 페이지는 고장 나 있었다.
- **쓰기 전에 실행 중인 원천을 읽고, 쓸 값을 먼저 보인다.** 운영 데이터 쓰기, API 호출, 계약에 의존하는 변경을 하기 전에는 실행 중인 시스템에서 스키마나 계약을 읽는다(데이터베이스 카탈로그, 서빙 리비전, 실제 설정 키). 노트·이전 요약·인계는 가설이다. DB·Redis·설정에 쓰기 전에는 쓸 값과 형식을 보여 주고 확인을 받는다. 예: 2026-09-29에는 이전 요약에서 가져온 열 이름 때문에 세 차례의 쓰기 전 읽기가 실패했다.
- **정본이나 공통 구조를 새로 정하기 전에 기존 설계를 찾는다.** 정본 테이블, 공통 스키마, 기준 규칙, 공식 처리 경로처럼 여러 소비자가 따를 것을 새로 정하거나 우회로를 만들기 전에, 관련 저장소들에서 같은 문제를 다룬 기존 설계(스키마·마이그레이션 파일, ADR·설계 문서, 관리자 API·작업)를 먼저 찾고 찾아본 범위와 결과를 밝힌다. 눈앞의 저장소나 운영 테이블만 보고 정하면 이미 있던 설계와 어긋나 결정을 뒤집게 된다. 예: 2026-11-21에 다른 저장소에 있던 기존 스키마 설계를 찾기 전에 정본을 정해 같은 날 번복했다.
- **설정도 데이터이며, 비밀값과 개인정보는 출력에 넣지 않는다.** 값을 읽으려고 환경·설정 파일을 `source`하거나 실행하지 않는다. 필요한 키만 골라, 값을 출력하지 않고 파싱한다. 토큰을 프로세스 인자에 넣지 않는다. 운영 로그와 설정 파일을 진단할 때도 넓은 `rg`나 로그 덤프로 훑지 않는다. 구조화된 필드나 좁힌 표지로 찾고 출력량에 상한을 둔다. 진단 출력에 뜻밖의 내용이 섞여 나오면 민감한 것으로 보고 노트·보고·후속 명령에서 뺀다.
- **고친 것과 신원이 실제로 도는지 실행 지점에서 확인한다.** 고쳤다, 커밋했다, 배포했다, 설정했다는 사실이 지금 실행되는 것이 그 판이라는 뜻은 아니다. 원격 기기는 pull하기 전의 판을 돌리고, `is-active`로 거른 재시작은 죽어 있는 서비스를 건너뛰고, 붙여넣은 옛 명령의 `VAR=값` 접두어는 바뀐 기본값을 덮고, 서비스 정의가 넘기지 않은 환경변수는 프로세스에 없다. 어느 계정·홈·자격으로 도는지도 같다. 파일이 있는지, 고정 경로, 캐시 파일에 적힌 계정으로 판정하지 않는다. 포착 신호: 이번 세션에서 고친 것을 다른 기기·다른 프로세스·예전에 적어 둔 명령으로 실행하려 할 때, 계정 전환 실패나 권한 없음을 진단할 때. 그 자리에서 실행될 판과 신원을 확인한다(대상 기기의 `git log -1`, 서비스 재시작 시각과 버전, `/proc/<pid>/environ`, `CLAUDE_CONFIG_DIR`·`CODEX_HOME`, 명령 앞의 환경변수, 도구가 찍는 계정 표시). 점검 결과에는 어느 판과 신원을 봤는지 적는다. 시험 실행은 바꾸는 모드가 아니라 검사 모드로 먼저 한다.
- **함께 쓰는 상태는 내 세션 것이 아니다.** 같은 기기의 git index와 stash, 체크아웃된 서브모듈, CLI의 전역 활성 계정, 브라우저 프로필 락, 여러 기기가 함께 고치는 저장소 파일은 다른 세션과 함께 쓰는 상태다. 포착 신호: 코드는 그대로인데 403, 락 오류, 되돌아간 포인터, 제목과 내용이 어긋난 커밋이 갑자기 나타날 때. 그때는 다른 세션부터 의심한다. 스테이징했으면 바로 커밋하고, `git add -A` 대신 경로를 지정한다. stash는 스택 위치가 아니라 `git stash create`가 돌려준 SHA로 다룬다. 전역 설정을 바꾸지 말고 명령마다 대상을 고정한다(`--configuration`, 토큰 환경변수). 자동 병합(`pull --autostash`, `stash pop`) 뒤에는 충돌 표식이 없는지 확인하고 나서 스테이징한다.

## 위임 (모든 도메인)

- **결과만 받으면 되는 일은 넘긴다.** 무거운 구현에서는 메인 세션이 작업의 판단에 집중하고, 진행 기록·메모리 정비 같은 메타 작업은 `core.md` → Persistence Hand-off에 따라 백그라운드 에이전트(scribe)에게 맡긴다. 많은 파일을 훑는 검색과 독립 검증도 같은 방식으로 위임한다. 가벼운 대화와 단순 작업은 메인 세션에서 처리한다. 나누는 비용이 아끼는 비용보다 크기 때문이다. 이 문장은 권고이지 통과 조건이 아니다.
- **서브에이전트 둘 이상을 동시에 돌리면 위임 현황판을 유지한다.** 돌아온 보고는 검증 결과가 아니다. `skills/autoloop/SKILL.md` §6a에서 설명하는 작은 현황판에 작업 단위마다 쓰기 범위, 상태, 아직 정리되지 않은 서로 간 영향을 적는다. 한 건만 위임할 때는 현황판을 쓰지 않는다.
- **격리가 득이 될 때는 worktree로 위임하되 생성물을 쓰는 의존성은 빌리지 않는다.** 기능 여럿을 나란히 만들거나, 오래 걸리는 리팩터링을 하거나, 되돌릴 수 있는 위험한 실험을 할 때는 `Agent({isolation: "worktree"})`로 위임한다. 단일 파일 편집, 읽기 전용 탐색, 이미 worktree 안에 있을 때는 하지 않는다. 메인 체크아웃의 `node_modules`를 심볼릭 링크로 빌린 worktree에서 코드 생성기가 돌면 원본 체크아웃이 바뀐다.

## 개발 (Dev)

- 조용히 고쳐서 실패를 가리지 않는다. 실행 중 오류가 나서 즉석에서 고쳤다면 반드시 보고한다. 작업자가 그 자리에 있어야만 통하는 수정이라면 자동화나 cron에서는 깨진다.
- 같은 실패가 두 번 되풀이되면 같은 방법을 세 번째로 시도하지 말고 접근을 바꾸거나 에스컬레이션한다.
- 승인한 계획을 온전히 지킨다. 승인한 계획은 실행 기준선일 뿐, 계획에 적히지 않은 기존 계약까지 고쳐도 된다는 허가가 아니다. 새 증거가 승인된 목표·수정 범위·제약·판정 기준을 바꾸거나, 계획이 명시적으로 없앤 동작을 복구해야 한다면, 재승인을 받기 전에 멈춰 충돌과 영향을 보인다. 그렇다고 아무 말 없이 다른 방법으로 돌아가도 된다는 뜻은 아니다.
- **요구나 명세가 모호하면 추측하지 말고 번호를 붙여 묻는다.** 요구·명세가 모호하거나, 서로 모순되거나, 당장 내려야 할 결정에 대해 아무 말이 없으면 행동하기 *전에* 사용자에게 번호를 붙인 확인 질문을 낸다. 내 해석을 밝히고 맞는지 확인받는다(AIA G716 RFI 모형). 답을 이미 알면서 기록을 남기거나 원하던 범위를 승인받으려고 묻는 낚시 질문은 하지 않는다.
- 명세·계약·요구사항·API·설계 문서를 쓰거나 고칠 때, 그리고 `docs/specs/`의 명세를 따라 작업할 때는 `discipline/spec.md`를 읽는다.

## 문서 (Document)

- 편집에는 삭제도 들어간다. 더하기만 하면 문서가 비대해진다. 먼저 바꾸지 않을 것을 정한 뒤 나머지를 다듬는다.
- 교차 참조의 무결성: 언급한 모든 절·파일·링크는 실제로 있어야 한다.

### 전달 (Transmission): 다른 사람이 읽을 때(맥락 없이 다시 읽을 미래의 자신도 포함)

글에도 `core.md` → After Acting → *See as a stranger*를 적용한다. 아래 세 검사에는 순서가 있다. 첫 검사가 판정을 정하고, 나머지 둘은 무엇을 찾아볼지 알려 준다.

- **문장을 판단하기 전에 독자를 정한다.** 줄여 써도 손해가 없는 것은 독자가 이미 그 뜻을 붙잡을 기준점을 갖고 있을 때뿐이다. 프로젝트명·ADR ID·팀 약칭처럼 일부가 함께 쓰는 이름은 내부자에게는 바로 통하지만 다른 사람에게는 뜻이 닿지 않는다. 그래서 *똑같은 문장*이 개인 노트에서는 괜찮고 인계 문서에서는 문제가 된다. 독자가 둘(그 이름을 아는 동료, 모르는 낯선 사람)인 문서는 한쪽에게 반드시 실패한다. 누구를 위해 쓰는지 밝히거나, 기준점이 되는 설명을 글에 넣는다.
- **삭제 검사 — 은유가 주장을 떠받치면 안 된다.** 비유하는 낱말을 지워 본다. 그래도 주장이 남으면 은유는 진술 *위에* 얹혀 있던 것이니 그대로 둔다. 잘 고른 비유는 주장을 더 또렷하게 전한다. 주장이 무너지면 은유가 진술 *자리를 대신하고* 있던 것이고, 독자는 무슨 뜻인지 스스로 짜 맞춰야 한다. 먼저 평이한 주장으로 다시 쓰고, 그래도 제 몫을 할 때만 유추를 더한다.
- **결정하지 않은 채 넘기지 않는다.** 압축한 "X 미정 / TBD / not decided"는 *누가, 정확히 무엇을, 왜 아직 열어 두는지*를 빼 버린다. 작성자는 셋 다 알지만, 독자는 빈칸만 물려받아 그것을 채우기 전에는 움직일 수 없다. 셋을 모두 쓰거나 항목을 문서에서 뺀다.

## 한국어 ↔ 영어 (Korean ↔ English)

### 한국어 입력 읽기

- 부정의 비대칭: 한국어는 중첩 부정을 행동을 다시 확인하는 방식으로 푼다("하지말까요? → 하지마"는 부정 요청을 확인하는 "정말 하지말까? → 진짜 하지마"로 읽히지만, 주로 영어로 학습한 모델은 이중 부정으로 잘못 풀어 *그 일을 해 버릴* 수 있다). 사용자의 대답이 예/아니오 확인에 대한 짧은 부정이면, 행동 전에 마음속으로 영어 "don't"로 다시 말한다. 행동이 비가역적이면 한 번 더 묻는다.
- 확인 뒤 거절이 이어지는 경우: "X 같이 커밋할까요? → 올리지마 → 강제 add 슛"은 알려진 실패 패턴이다. 바로 다음 행동에는 사용자의 *이전 턴 거절*을 약한 선호가 아니라 강한 거부로 본다.
- 사용자 지시를 문체로 해석해 번역하지 않는다. 반존대·반말·격식체 차이는 어조일 뿐 명령 강도 차이가 아니다. 명령의 요구 수준은 어휘만 보고 읽으며, 어조와 분리한다.

### 한국어 출력 쓰기

- **영어에서 닳은 은유는 한국어로 옮기면 다시 살아난다.** `stance`, `orthogonal`, `reside`, `surface`, `land`, `deflationary`는 영어에서는 닳아 평평한 말이라 독자가 곧장 주장으로 지나간다. 이 말들을 한국어로 옮기면(자세, 직교, 거주) *살아 있는 비유*로 되살아나서, 독자는 주장에 닿기 전에 먼저 그 이미지를 풀어야 한다. 풀어 봐도 주장이 없을 때도 있다. 같은 저자가 영어 규율 문서는 또렷하게 쓰면서 한국어 노트는 흐리게 쓰는 까닭이 여기에 있다. 이 실패는 영어 말을 한국어로 들여올 때만 생겨서, 영어로 쓰는 쪽에서는 보이지 않는다. 한국어 초안을 쓸 때는 영어에서 옮겨 온 추상어마다 삭제 검사(§ 문서 (Document) → 전달 (Transmission))를 적용한다.
- **전보식 한국어는 말뿐 아니라 논항도 뺀다.** 한국어는 조사와 서술어를 버려 압축한다(`흡수 결정 X`, `직교로 보면 얕음`). 이때 *누가 / 무엇을 / 왜*도 함께 사라진다. 영어 약기는 대체로 동사와 그 논항을 남긴다. 영어 노트에서는 안전한 압축도 한국어에서는 손실을 만든다. 논항을 다시 풀어 쓴다.
