# 2026-11-23 — 힌트는 가장 약한 집행 수단이다

## Context

`hints.md`는 지난 실패가 다음 행동에 닿는 유일한 경로였다. 함정 기록(`trap_*.md`)은 행동하는 순간에
읽히지 않고, `hints.md`만 모든 세션과 작업자에게 실린다. 그래서 같은 실패가 두 번 나면 힌트로 올리고,
다시 나면 그 힌트의 사례 목록에 더하는 방식으로 운영했다.

2026-11-22에 잰 상태는 다음과 같았다.

- 메인테이너의 함정 기록은 82개, 16만 자였고 매달 10~15개씩 늘었다. 힌트가 인용하는 것은 28개였다.
- `hints.md`는 13,239자였다. 승격할 때마다 힌트가 하나씩, 약 650자씩 늘었고 줄어드는 단계는 없었다.
- 명세 절(작성 6개, 따르기 5개)은 `sonmat.spec_awareness: enabled`를 선언한 프로젝트에서만 의미가
  있는데, 메인테이너 기기에서 그 플래그를 켠 프로젝트는 하나도 없었다. Codex 전체 접근 권한 절도
  해당 Codex 세션에서만 쓰이지만 Claude 세션에도 매번 실렸다.

모든 단계가 덧붙이기만 했다. 사례가 쌓일수록 새 함정과 기존 82개를 견주는 계열 확인은 사실상
설명 줄만 훑는 일이 됐다. 힌트가 하나 늘 때마다 나머지 힌트가 떠오를 확률도 떨어진다(추론이다).
힌트가 발동해서 막은 일은 기록되지 않으므로 효과를 잴 방법도 없다.

기록은 힌트의 한계도 보여 준다. 셸 명령 `pkill -f`가 자기 셸을 죽이는 함정은 경고가 적혀 있는데도
여섯 번 재발했고, PreToolUse 셸 가드로 막은 뒤에야 멈췄다. pCloud 작업 트리의 stash 오염 기록에는
"문서 경고만으로 재발을 못 막았다"고 적혀 있다. 2026-11-22에는 다른 기기의 자동 동기화가 손맛 하위
모듈 포인터를 되돌렸는데, 이 계열은 `hints.md`에 사례로 올라 있었다. 훅은 힌트를 읽지 않는다.

## Decision

힌트를 교훈 저장소가 아니라 가장 약한 집행 수단으로 본다. 교훈이 갈 곳은 세 가지다.

1. 특정 명령·파일·이벤트에서 기계적으로 가려낼 수 있으면 코드(훅·가드·도구)로 막는다. 여러 하네스에서
   같은 행동이 일어나면 하네스 훅보다 git 훅이나 도구 자체를 고른다. 코드가 생기면 힌트는 지운다.
2. 판단이 필요하고 포착 신호가 구체적이면 `hints.md`에 둔다. 힌트에는 규칙, 포착 신호, 할 일, 대표 예
   하나만 적는다. 근거 함정 목록은 메모리 쪽 `hint-evidence.md`로 옮긴다.
3. 특정 작업에서만 필요하면 그 작업이 읽는 파일에 둔다. 명세 규율은 `discipline/spec.md`로,
   Codex 전체 접근 권한 규율은 `discipline/codex-full-access.md`로 옮겼다. SessionStart 훅은
   Codex 전체 접근 권한 세션과 명세 플래그를 켠 프로젝트에서만 그 파일을 읽으라고 알린다.

`hints.md`는 8,000자를 넘기지 않는다. 넘게 되면 새 힌트를 더하지 말고 기존 힌트와 합치거나 더 큰
원칙으로 흡수한다. scribe의 계열 확인 규칙도 이 순서를 따르게 고쳤다.

이번 재구성에서 항목 48개를 다음처럼 처리했다.

| 처리 | 항목 |
|---|---|
| 유지 | 증거보다 넓게 주장하지 않기, 기존 설계 찾기, 설정도 데이터, 함께 쓰는 상태, 위임 두 개, 조용히 고치지 않기, 승인한 계획 지키기, 모호하면 번호 붙여 묻기, 문서 두 개, 전달 세 개, 한국어 다섯 개 |
| 병합 | "어느 신원으로 도는지"를 "고친 것이 실제로 도는지"에 합쳤다. 개발 절의 "데이터 쓰기 전 계획"을 "쓰기 전에 실행 중인 원천을 읽는다"에 합쳤다. worktree 격리는 위임 절로 옮기며 `node_modules` 함정을 붙였다 |
| 이동 | 명세 작성 다섯 개와 명세 따르기 다섯 개 → `spec.md`. Codex 전체 접근 두 개 → `codex-full-access.md` |
| 다른 문서가 덮음 | 검증 전에 줄이기, 체계적 디버깅, 끝난 뒤 자기 검토. `core.md`와 메인테이너 전역 지침의 코드 분량 규율이 이미 다룬다. 디버깅 항목의 "같은 실패 두 번이면 바꾼다"만 개발 절에 남겼다 |
| 뺌 | TDD 기본, 커밋 단위, 깊은 모듈, AI/ML 네 개, 분석 두 개. 기록된 실패가 없는 작업 방침이나 교과서 지식이다. 메인테이너 쪽 코딩 지침과 메모리로 옮겼다 |

결과는 13,239자에서 6,256자다.

## 버린 대안

- 가족 색인(`FAMILIES.md`)을 먼저 만드는 안. 계열 확인의 비용은 줄이지만 쌓이는 구조는 그대로 둔다.
  출구를 고치는 것이 먼저라고 봤다. `hint-evidence.md`가 그 색인의 가벼운 형태다.
- 사례를 그대로 두고 분량만 줄이는 안. 사례 목록은 파일의 13%뿐이었고, 늘어나는 원인은 승격마다
  힌트가 더해지는 데 있었다.

## Consequences

- 코드로 옮길 후보인 "설정도 데이터"와 "함께 쓰는 상태", 교차 참조 검사는 가드가 생길 때까지 힌트로
  남긴다. 가드 작업은 메인테이너의 하네스 설정 리포와 안채 git 훅에서 따로 한다.
- 힌트에서 사례 목록을 지웠으므로 근거를 찾으려면 `hint-evidence.md`를 본다. 그 파일이 없는
  독립 설치에서는 scribe가 처음 승격할 때 만든다.
- 뺀 항목이 조용히 지켜 주던 행동이 있었는지는 잴 수 없다. 개발 방침은 프로젝트 지침이 맡는다.
