# sonmat v0.9 — 증인을 세우다

> 2026-04-15. sonmat v0.9.0 / v0.9.1 릴리스 노트이자, 그 하루를 만든 설계 사건.

요약부터: sonmat에 **sonmat-witness**라는 외부 검증 에이전트를 넣었다. 메인 세션이 작성한 산출물이 사용자가 실제로 요청한 것과 일치하는지, **메인의 추론을 읽지 않고** 판정한다. 그리고 이 에이전트를 도입하는 과정에서 우리가 한 세션 안에 세 번이나 "매력적인데 틀린 가정"을 발견했고, 세 번 다 devil's advocate을 돌리자 뒤집혔다. 이 글은 둘 다에 대한 이야기다.

---

## 왜 witness였나

sonmat은 "Claude(또는 다른 LLM)가 자기 작업을 스스로 검증하게 두면 안 된다"는 단순한 관찰에서 시작한다. 사람도 똑같다 — 자기가 쓴 글을 자기가 교정하면 오타를 못 본다. 수술실에서는 의사 본인이 Time Out을 낭독하지 않는다. 비행기에서는 조종사가 스위치 위치를 말로 대답하면 검증이 안 되고, 다른 조종사가 **스위치 자체**를 확인해야 검증이 된다.

같은 원리를 LLM에 적용하려면 두 가지가 필요하다.

1. **검증자가 실행자의 추론에 접근할 수 없어야 한다.** 접근하면 실행자의 합리화를 그대로 상속받아 "고무도장"이 된다.
2. **검증자의 입력은 사용자의 원문이어야 한다.** 메인이 "사용자가 원한 것"으로 해석한 버전이 아니라, 사용자가 실제로 친 문장 그대로.

기존 sonmat의 `guard` 스킬은 이 둘 중 어느 것도 해결하지 못했다. guard는 메인 세션 안에서 돌아가는 규칙 체크라 메인과 같은 맥락을 공유한다. 테스트 실행, 민감 파일 차단, 디시플린 준수 같은 **운영 수준** 체크에는 적합하지만, "사용자가 요청한 것과 산출물이 일치하는가"를 묻는 데는 적합하지 않다. 구조적 격리가 없기 때문이다.

그래서 witness를 분리했다. witness는:

- **Task tool로 스폰되는 서브에이전트**. Claude Code가 제공하는 execution-level 컨텍스트 격리를 받는다.
- **입력은 raw user turn과 산출물만**. 메인의 설명, chain-of-thought, 코멘트, 커밋 메시지는 읽지 못하거나 읽어도 인용할 수 없다.
- **citation이 필수**. 모든 발견은 `user turn N: "exact quote"`와 `file:line` 쌍을 가져야 한다. 근거 없이 "느낌이 이상하다"는 발견은 구조적으로 버려진다.
- **source-based verdict**. `BLOCK`/`WARN`은 witness가 느낌으로 정하지 않는다. 어느 체크(§1 intent-scope, §2 intent-content, §3 framing-derived, §4 ground truth)가 발견을 냈느냐로 자동 결정된다. `§1/§2/§4` → `BLOCK`, `§3` → `WARN`. 강도 판정 자체를 제거했다.

그리고 세 가지 scope에서 작동한다: 커밋 하나(`commit gate`), 세션 전체 파일 변경(`session forest`), 그리고 사용자가 "전체적으로", "모든 X에", "시스템 전반" 같은 범위 확장 지시를 했을 때의 `principle coverage`. 마지막이 가장 날카로운 모드로, 여러 파일에 걸친 원칙 적용이 일부만 됐는지를 witness가 직접 grep한다.

witness 설계 자체는 이 정도다. 하지만 이번 릴리스를 만든 진짜 사건은 설계 뒤에 있었다.

## 한 세션에 세 번 뒤집힌 가정

witness를 만드는 동안 나는 세 번, **같은 종류의 실수**를 했다. 매번 매력적으로 들리는 이름이나 구조를 먼저 받아들이고, 그 프레임 안에서 설계를 진행했다. 그리고 매번 devil's advocate 스킬(`/devil`)을 돌리자 해당 가정이 **load-bearing**(전체를 떠받치는 핵심 가정)이고 실제로는 약하다는 것이 드러났다. 세 번 다 뒤집혔다.

### 1차: "session-orchestrator-worker 3층 구조"

sonmat memory에 쓰여 있던 문장: "역전된 3층 구조 설계 진행." 메인 세션은 대화자로, 그 아래에 오케스트레이터가, 그 아래에 워커가. witness는 이 3층 구조 위에 얹히면 완벽해 보였다.

devil CCT를 돌렸다(`/devil`의 내부 discovery 단계 — 주장의 load-bearing 한 줄을 먼저 찾는 과정):

- **Claim-crux**: 이 구조는 "Claude Code가 nested subagent delegation을 지원한다"는 가정에 기댄다.
- **Counter-fit**: 공식 문서를 읽지 않고 구조부터 그렸다는 증거. 검증 안 됐다.

그래서 공식 문서를 확인했다. Claude Code의 [multi-agent 문서](https://platform.claude.com/docs/en/managed-agents/multi-agent.md):

> "Only one level of delegation is supported: the coordinator can call other agents, but those agents cannot call agents of their own."

명시적으로 금지. 3층 구조는 **구조적으로 불가능**. "역전된 3층"이라는 매력적인 이름이 한 달 전 메모리에 박히는 순간 이후의 모든 설계 논의가 그 프레임 안에서 돌아갔고, 플랫폼이 그 프레임을 지원하는지는 아무도 확인하지 않았다.

2층(`witness-pair`)이 현재 Claude Code에서의 천장이고, 우리는 이미 거기에 도달해 있었다. 3층은 허상이었다.

### 2차: "PreToolUse hook이 witness를 스폰해서 tool call을 deny한다"

3층을 retract하고 나서, 다음 설계는 "autoloop의 커밋 단계에서 PreToolUse hook이 witness를 agent-type 훅으로 스폰하고, witness가 BLOCK을 내면 hook이 tool call을 deny한다"였다. 이것도 매력적이었다 — 메인이 witness를 우회할 수 없는 플랫폼 레벨 강제.

그런데 이 파이프라인이 실제로 문서화되어 있는가? 다시 공식 guide를 확인했다:

- `agent` 타입 hook은 존재한다. 문서화되어 있다.
- 하지만 **PreToolUse 이벤트에서의 agent hook + verdict-based deny** 예시는 **0개**. 모든 공식 예시는 `Stop` 이벤트에서 테스트 통과를 확인하는 용도.
- "hook이 서브에이전트를 synchronous하게 기다렸다가 verdict로 deny를 populate한다"는 semantics 자체가 문서에 없다.

devil CCT를 다시 돌렸다.

- **Claim-crux**: witness가 **hook 레이어 강제**를 필요로 한다는 전제.
- **Counter-fit**: autoloop `[Judge]` 단계는 이미 모든 phase가 디시플린 기반으로 돌아간다(`[Plan]`, `[Define]`, `[Execute]`, `[Evaluate]`). witness gate만 특별히 플랫폼 레벨 강제가 필요하다고 가정할 근거가 없다.
- **Cause-chain**: "hook 강제 → 신뢰 가능한 게이팅" 인과는 hook이 존재할 때만 성립. hook이 없는 지금, 대안은 autoloop 디시플린 — 그리고 autoloop는 **이미 그렇게 작동한다**.

뒤집혔다. witness는 hook이 필요 없었다. **Task tool로 `[Judge]` 단계 안에서 스폰**하면 된다. Task tool + `subagent_type`은 잘 문서화된 primitive. autoloop가 다른 phase를 실행하는 것과 똑같은 방식으로 witness를 실행한다. 엔포스먼트는 autoloop discipline — 이미 받아들인 "디시플린 잔존분".

### 3차: "witness는 결정론적 comparator다"

여기까지 오니 witness는 shippable해 보였다. 실행 격리도 있고, 입력도 raw user turn이고, citation rule도 있고. 마지막으로 한 번 더 devil을 돌려봤다 — 이번엔 witness 자체를 공격.

주장: "witness는 우리가 설계한 대로, 비교만 하고 reasoning은 하지 않는 결정론적 comparator처럼 작동할 것이다."

- **Claim-crux**: 프롬프트에 "do not reason, compare"라고 적으면 LLM이 실제로 그렇게 행동한다는 가정.
- **Counter-fit**: witness는 agent file 한 장이 아니라, **agent file + 입력 + 모델의 기본 경향** 조합으로 행동한다. 같은 클래스의 LLM이 메인을 돌리고 witness를 돌린다. 메인이 자기 검증에서 rationalization에 빠지는 바로 그 failure mode가 witness에도 적용될 수 있다 — 단지 우리가 "비교만 해라"라고 적어뒀기 때문에 빠지지 않을 거라는 보장은 없다.
- **Cause-chain**: "agent file의 규칙 → 엄격한 comparator 행동"의 인과는 약하다. enforcement 메커니즘이 witness가 제약해야 하는 바로 그 메커니즘(프롬프트 지시에 대한 instruction-following)이라는 순환 구조.

이번 것의 반전이 가장 흥미로웠다. **Strong form**(witness는 결정론적 comparator)은 weakened. **Weak form**(witness는 메인 self-check보다 여전히 낫다)은 holds. 이유:

```
Layer 1 — 실행 격리 (harness-enforced) ───── 진짜 구조적 보장
Layer 2 — spawn prompt 규율 ─────────────── aspirational contract
Layer 3 — citation rule ──────────────────── aspirational contract
```

Layer 1은 플랫폼이 강제한다. witness가 sloppy해져도 메인의 합리화 컨텍스트에 접근할 수 없다 — confirmation-rubber-stamp failure mode에 빠질 방법이 없다. 이게 input isolation 하나만으로도 메인 self-check보다 나은 이유다.

Layer 2와 3은 LLM 프롬프트 수준의 행동 계약이다. 런타임에 enforce되지 않는다. witness가 내부적으로 "이 finding은 §2인데 약해 보이니 WARN으로 해야지"라고 결정하면 그걸 구조적으로 막을 수단이 없다.

이 차이를 문서에 honest하게 반영한 것이 v0.9.1. `witness.md`의 `§Isolation stack`은 세 layer를 명시적으로 enforced vs aspirational로 분리한다. 그리고 **early use에서 사람이 직접 verdict를 sample해서 layer 2-3이 실제로 버티는지 확인해야 한다**는 지시를 넣었다. drift가 관찰되면 agent file을 조정한다. scribe가 이미 witness verdict를 journal에 기록하므로, drift 감지 채널은 준비되어 있다.

witness는 완벽한 검증자가 아니다. 하지만 메인보다는 낫고, 그 차이는 layer 1 덕분에 **거짓 없이 보장**된다. 나머지는 현실과 맞춰가며 튜닝할 영역이다.

## 메타 관찰 — discovery-led depth가 스스로에게 적용됐다

이번 세션에 같이 들어간 중요한 변화가 하나 더 있다. `inspect`와 `devil`과 `punch`의 설계 원칙을 **discovery-led**로 재정렬했다. 원래는 "cascade 원칙"이라고 불렀는데, 그 단어가 방향을 명확하게 전달하지 않아서 이름을 바꿨다.

핵심은 간단하다: **깊이는 발견 다음에 온다**. 파고들지 말지 먼저 정하고 나서 뭔가를 찾는 게 아니라, 뭔가를 발견했을 때 그 발견이 깊이를 끌어당긴다. 체스에서 long variation을 계산하기 전에 먼저 Checks/Captures/Threats를 훑는 CCT, 수술 전 Time Out, 항공 challenge-and-response에서 PM이 switch position을 "본다"는 행위 — 다섯 가지 검증 전통이 모두 같은 구조를 공유한다.

devil에도 CCT의 이름을 빌려다 적용했다(Claim-crux / Counter-fit / Cause-chain). 주장을 평행 공격으로 네 축에서 때리는 대신, 먼저 **load-bearing assumption 하나**를 찾고, 그것이 Evidence 축인지 Logic 축인지 Alternatives 축인지에 따라 그 한 축에만 깊이를 투입한다. 나머지 축은 가벼운 패스.

오늘 세 번의 devil 라운드가 이 원칙의 첫 실전 적용이었다. 만약 평행 공격이었다면 "witness는 좋은가, inspect는 좋은가, punch는 좋은가, 3층은 좋은가, hook은 좋은가"를 동시에 공격했을 것이고, 결론이 이렇게 선명하게 나오지 않았을 것이다. CCT는 매번 정확히 **한 개의 load-bearing 가정**을 집었고, 그 한 가정만 깊이 파자 전체 결론이 뒤집혔다. 우리가 설계한 원칙이 스스로에게 적용됐고 작동했다.

## v0.9에 들어간 것들 (요약)

- **sonmat-witness**: 외부 intent-artifact comparator. 3 scope scale(commit / session forest / principle coverage). Source-based verdict(`BLOCK`/`WARN`/`PASS`/`INSUFFICIENT_GROUND_TRUTH`).
- **guard / scribe 분리**: guard는 순수 검증(운영 체크 + 발견), scribe는 사후 persistence(project rule 기록, novel trap memory, journal, bridge note, witness verdict 로그).
- **discovery-led 원칙 재정렬**: inspect는 trigger-reactive depth, devil은 CCT로 load-bearing 찾아서 asymmetric attack, punch는 user invocation 자체가 discovery인 모드 시스템.
- **punch refactor-residue check**: 구조적 제거/renaming 이후 살아남은 stale reference를 mechanical grep으로 탐지. Section/function/file/terminology/example/enum/template 7가지 패턴.
- **Isolation stack 솔직한 framing**: layer 1(harness-enforced) vs layer 2-3(aspirational). 강한 용어로 포장하지 않고 어느 부분이 보장이고 어느 부분이 희망인지 문서에 직접 분리.
- **Feature request 문서**: 현재 플랫폼이 제공하지 않는 4가지 primitive(input channel 제한, nested delegation, session layer, 문서화된 hook pattern)를 정리. `docs/feature-requests/claude-code-isolation.md`.

v0.9.0 — witness + 재구조. v0.9.1 — honest framing pass.

## 교훈 한 줄

**매력적인 아키텍처 이름은 설계 전에 플랫폼 지원 여부를 확인하라.** "역전된 3층", "PreToolUse agent hook + deny", "결정론적 comparator" — 세 이름 모두 그럴듯했고, 세 번 모두 실제로는 성립하지 않았거나 약했다. devil CCT가 매번 정확히 그 틈을 집었다.

다른 말로 하면: 이 원칙을 문서에 박아두는 데서 끝나는 게 아니라, 그 원칙이 **자기 자신에게** 어떻게 적용되는지 관찰해야 한다. 오늘 세션이 그 관찰의 첫 장이었다.
